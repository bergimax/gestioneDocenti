# Task template

Every issue is groomed into these four sections before anyone implements it.

## Goal
One sentence: what is true after this task that is not true now.

## Description
What to change and why, with the files, functions and spec sections (§) it touches. Decisions already taken are stated
as decisions. Enough for an engineer who has not spoken to the PM.

## Acceptance criteria
A checklist. Each item is something one can point at (a screen, a response, a test name, a command output) and answer
yes or no. Include the edge cases: empty data, wrong role, stale version, expired token, invalid input.

## Out of scope
What this task deliberately does not do. Each item links to a follow-up issue.
